1. Опишите ADR, который проиллюстрирует причину изменения любой из коммуникаций.
### ADR 1: Исправяем проблему с попаданием неактуального рейтинга заданий в сервис бонусов из сервиса найма.

#### Status. Proposed

#### Context.
На момент принятие решения бизнес планировал начислять менеджерам зависящее от рейтинга количество бонусов за выполнение кандидатом в ученики созданного ими задания. Бизнес логика состояла из двух коммуникаций: синхронный вызов зачисления средств и отправки асинхронного события с рейтингом задачи TaskRating из сервиса найма в сервис бонусов.
К сожалению, у бизнеса возникли проблемы с такой реализацией коммуникации, которые выглядели так:
- Некорректное начисление бонусов из-за неактуального рейтинга.

Эти проблемы возникли из-за eventual consistency, которая возникла из-за асинхронной коммуникации. Чтобы решить эту проблему, нужно добиться strong consistency рейнтинга в сервисе бонусов.

#### Decision.

Единственный способ решить проблему перехода с eventual consistency на strong consistency — перевести связь с асинхронной на синхронную. Так как синхронная связь может быть только request-response, то остаётся выбрать способ имплементации в коде.

Будем использовать http-вызов из сервиса бонусов в сервис найма (pull - модель).

#### Consequences.

- Плюсы:
  - Закрываем проблему с неактуальным рейтингом
  - Упрощение коммуникации (синхронный вызов проще)
- Минусы:
  - Процесс начисления бонусов зависит от живости сервиса найма
  - Дополнительная нагрузка на сервис найма

#### Alternatives.
- Оставить асинхронную коммуникацию и добавить ретраи: не решает проблему актуальности рейтинга.
- Push модель синхронной коммуникации (из сервиса найма делаем http request с рейтингом в сервис бонусов)
  - Проверка домашек будет падать при недоступном сервисе бонусов, кандидаты в ученики будут страдать.
  - При упавшем сервисе найма сервис бонусов будем использовать неактуальный рейтинг.

3. Фитнесс функций для Scalability и Reliability характеристик. 
- Scalability
  - Система должна выдерживать одновременную работу 100 менеджеров. (holistic, manual, trigerred, threshold)
  - В случае увеличения нагрузки на сервис найма должен подняться его дополнительный инстанс за менее чем 2 минуты. (atomic, automated, triggered, threshold)
  - Система должна выдерживать увеличение количества кандидатов в учителя, одновременно решающих задания, без значительного ухудшения производительности. Запускаем каждую неделю, результаты прогонов оставляем и потом анализируем возможную регрессию. (holistic, automateed, continous, trend)
- Relability
  - Информация о выполнении задания кандидатом в учителя не должна теряться даже при сбоях системы. (atomic, automated, triggered, threshold (0 потерянных событий))
  - События о выполнении заданий кандидатами должны стабильно обрабатываться, без длительного накопления необработанных событий. Непрерывно собираем Consumer Lag, анализируем изменения за последнюю неделю. (atomic, automated, continuous, trend)
  - Каждый из сервисов должен быть способен восстановиться при падении без потери данных. (holistic, manual, triggered, threshold).
